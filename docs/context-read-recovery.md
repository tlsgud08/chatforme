# 대화 문맥 조회의 연결 오류 복구

첨부 오류: `대화 문맥 불러오기 실패: TypeError: Load failed`.

## 확인한 회귀

PR #133 이전 전송 경로는 `messages`를 GET으로 읽었습니다. 이후에는
`session_generation_context` RPC를 기본 POST 방식으로 호출합니다.
잠금 파일의 `@supabase/supabase-js 2.106.2` / PostgREST 구현은 GET의 연결
실패를 최대 3회 재시도하지만 POST는 재시도하지 않습니다. 따라서 동일한
일시적 연결 끊김이 최적화 뒤에는 곧바로 전송 실패로 드러납니다.
초기 메시지 페이지 RPC에도 같은 문제가 있습니다.

실제 SDK와 `TypeError('Load failed')`를 사용한 시험에서 기존 POST는
한 번 만에 실패하고 수정 GET은 두 번째 요청에서 복구하는 것을 확인했습니다.
브라우저가 연결을 끊는 최초 원인 자체를 이 결과로 확정할 수는 없습니다.

## 운영 확인 (2026-10-24 KST)

- 운영의 두 함수가 존재하며 STABLE / SECURITY INVOKER임을 확인했습니다.
- 최근 24시간 edge 로그의 문맥 조회 218회, 메시지 페이지 조회 98회는 모두
  HTTP 200이었습니다. 문맥 조회의 최대 origin time은 1,842ms였습니다.
- 누적 쿼리 통계의 문맥 조회 평균 실행 시간은 약 123ms, 최대 약 819ms였습니다.
- 별도의 PostgREST `Warp server error: Thread killed by timeout manager`
  기록이 있으나, 그 기록과 첨부 실패의 직접적인 인과관계는 확인하지 못했습니다.
- 서버에 도달하지 않거나 응답 수신 중 연결이 끊긴 요청은 위 200 기록만으로
  정상 수신을 보장할 수 없습니다. 운영 DB/권한/데이터는 변경하지 않았습니다.

## 수정

- 두 읽기 전용 RPC만 `{ get: true }`로 호출하여 기존 SDK의 제한된 재시도를
  사용합니다. 별도 전역 재시도를 중첩하지 않습니다.
- 첫 페이지는 커서를 생략합니다. GET URL에 `before_turn=null`을 넣으면 정수
  파라미터가 잘못되므로 `undefined`를 사용합니다. 커서 0은 그대로 전달합니다.
- 방 진입 조회 전체에 취소 신호를 전달하여 이동/재시도 때 남은 요청을 취소합니다.
- 재시도까지 실패하면 같은 방에서 다시 불러올 수 있습니다. 필수 프롬프트나
  설정을 못 읽은 상태로 임의의 기본값을 사용해 모델을 호출하지 않습니다.
- `Load failed`를 연결 오류로 안내하고, 사용자가 취소한 문맥 조회는 오류로
  알리지 않습니다. 조회 실패 시 기존 입력 복원과 전송 잠금 해제를 유지합니다.
- 쓰기 RPC, 유료 모델 호출, 대화 본문/요약/키워드/리롤 구성은 변경하지 않습니다.
  데이터 캐시를 추가하지 않으며 RLS와 소유자 검사는 그대로 적용됩니다.

## 검증

`npm run test:context-recovery`는 실제 SDK로 기존 실패, 연결 복구, 3회 재시도
한도, 권한/스키마 오류의 즉시 반환, 커서/리롤 인자, 취소와 쓰기 비반복을 검사합니다.

`npm run test:browser:loading`은 실제 프로덕션 빌드에서 메시지 조회 한 번 실패,
문맥 조회 한 번 실패 후 복구, 모델 호출 1회, 지속 실패 시 입력 복원/쓰기 0회,
같은 방 수동 재시도와 기존 배포/스크롤/검색 회귀를 검사합니다.

실행 결과: 전체 기존 시험, Node 22 타입 검사·프로덕션 빌드·연결 복구 시험,
Chromium 브라우저 시험이 통과했습니다. 브라우저에서 문맥 조회는 두 번째
요청으로 복구했고 모델은 1회 호출됐습니다. 지속 실패 시 최초 요청을 포함해
4회 뒤 중단되었으며 쓰기와 모델 호출은 0회였습니다. 편집 전후 스크롤은
`6424 → 6424`, 생성 전후 스크롤은 `200 → 200`이었습니다.
네트워크 실패와 모델 응답은 모두 모의 처리했으며 유료 호출은 하지 않았습니다.

추가 SQL은 필요하지 않습니다.
