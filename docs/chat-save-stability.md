# 2026-10-24 저장·구버전 앱 점검

- PR #136은 한국 시간 21:43에 병합됐고 GitHub의 Vercel 상태는 성공입니다.
  실제 `https://inuchat.vercel.app/`에서 받은 최신 ChatPage 번들에도 읽기 RPC의
  `{get:true}`가 포함되어 있습니다.
- 그런데 22:06까지 iPhone Safari에서 보낸 문맥·메시지 페이지 조회는 여전히
  POST였습니다. 첨부의 원문 `메시지 편집 실패: TypeError: Load failed`도 최신
  오류 분류 문구와 다릅니다. 열린 클라이언트에 구버전이 남은 증거입니다.
- 새 서비스워커는 기존 탭의 코드와 작성 내용을 보존하기 위해 대기합니다.
  기존 코드에는 이 대기 상태를 사용자에게 알리는 화면이 없었습니다.
- 저장 요청이 수십 ms 간격으로 이어지는 운영 기록이 있습니다. 임시저장 큐는
  첫 요청만 interval을 기다리고, 요청 중 들어온 새 스냅샷은 즉시 연속 저장합니다.
  실제 기존 소스를 결정적 시계로 실행하여 설정 간격을 무시하는 실패를 재현했습니다.
- HTTP 200/204 기록은 브라우저가 응답을 받았다는 보장이 아닙니다. 편집의 PATCH
  응답이 끊기면 기존 코드는 실제 저장 여부를 확인하지 않고 실패를 표시했습니다.
- 브라우저의 최초 연결 끊김 원인은 아직 특정하지 못했습니다. 모의 연결 실패를
  재현한 것은 운영의 모든 연결 문제가 해결됐다는 뜻이 아닙니다.
- Vercel 팀 API는 현재 연결 권한으로 403이어서 상세 배포 로그를 조회하지 못했습니다.
  위 배포 확인은 GitHub 상태와 실제 공개 사이트의 최신 파일에 근거합니다.

## 수정

1. 임시저장은 각 요청 완료 후 간격을 지킵니다. 중간 스냅샷은 최신 내용으로
   합치며, 생성 종료 시 flush는 대기 없이 최신 내용을 저장합니다. 최종 저장 후
   stop이 예약된 쓰기를 취소하는 동작을 유지합니다.
2. 편집은 메시지 ID·방 ID·content_version·기존 명령어 필드를 조건으로 저장하고
   반환된 행으로 화면의 버전도 갱신합니다. 응답이 끊겼다면 먼저 서버 값을 읽습니다.
   이미 같은 내용이면 성공으로 복구하고, 여전히 원본이면 조건부 저장을 한 번만
   더 시도합니다. 다른 탭의 변경은 덮어쓰지 않습니다. 저장 여부도 읽지 못하면
   확인할 수 없다고 알리고 편집창과 입력을 유지합니다.
3. 새 워커가 대기하면 모든 관련 탭/설치 앱을 닫고 다시 열어야 한다는 안내를
   표시합니다. 강제 새로고침·skipWaiting·캐시 삭제를 하지 않습니다. 복귀 시 업데이트
   확인은 1분당 최대 1회이며 DB 조회를 추가하지 않습니다.

## 검증

- 실제 SDK: 편집 요청 전 끊김, 서버 반영 후 응답 끊김, 응답 본문 수신 실패,
  늦은 최초 커밋, 버전·명령어 충돌, 권한 오류, 결과 확인 실패, 재시도 상한 검사.
- 결정적 시계: 요청 중 새 글자가 들어와도 임시저장 간격 유지, 즉시 최종 flush,
  stop 이후 예약된 쓰기 취소 검사. 기존 소스는 간격 검사에서 실패합니다.
- 실제 PWA 두 버전과 Chromium: 대기 버전 안내, 끊긴 편집의 화면 복구,
  중복 없는 저장, 기존 독립 스크롤·생성·조회 실패 복구·모바일 UI 회귀 검사.
- 운영 DB·데이터·권한은 변경하지 않았고 추가 SQL도 필요하지 않습니다.

전체 `npm test`, Node 22 타입 검사·프로덕션 빌드·저장 안정성 시험, Chromium
PWA 회귀 시험이 통과했습니다. 편집 전후 스크롤은 `6424 → 6424`, 생성 전후는
`200 → 200`을 유지했습니다. 브라우저의 API·모델 응답은 모의 처리했습니다.

새 코드를 배포해도 이미 열린 구버전 화면은 자동 교체되지 않습니다. 작성 중인
